# 三角洲登录失败分析

对比对象：

- **A 组（能登录）**：`老八数据号root版上号器1.1[四合一].apk`
- **B 组（登录失败）**：本仓库 `wsw0803/shq`

结论先行：**B 组不是「参数没调对」，而是架构上缺少了 A 组赖以成立的那一层。**
仅修改 `GameLaunch` 的候选顺序、重试次数、Intent 附加项，都无法让三角洲通过登录。

---

## 一、A 组的真实形态

从 APK 的 `AndroidManifest.xml` 直接读出：

```xml
<meta-data android:name="xposedmodule"        android:value="true"/>
<meta-data android:name="xposedminversion"    android:value="54"/>
<meta-data android:name="xposeddescription"
    android:value="支持过腾讯健康系统和root不卸载qq登录"/>
```

它不是「上号器」，是 **Xposed 模块**。核心类：

```
com.tencent.TrustBypassHook
    implements de.robv.android.xposed.IXposedHookLoadPackage
    implements de.robv.android.xposed.IXposedHookZygoteInit
```

---

## 二、A 组到底 hook 了什么（已完整还原）

A 组对这些字符串做了 StringFog 加密。算法是标准 XOR 实现
（`com.github.megatronking.stringfog.xor.StringFogImpl`）：

```java
private static byte[] xor(byte[] data, byte[] key) {   // 原地修改并返回
    int i = 0;
    for (int k = 0; k < data.length; k++) {
        if (i >= key.length) i = 0;
        data[k] ^= key[i++];
    }
    return data;
}
public String decrypt(byte[] data, byte[] key) {
    return new String(xor(data, key), StandardCharsets.UTF_8);
}
```

还原结果：

| 字段 | 明文 |
|---|---|
| `SSL_CLASS_NAME` | `com.android.org.conscrypt.TrustManagerImpl` |
| `SSL_METHOD_NAME` | `checkTrustedRecursive` |
| `SSL_RETURN_TYPE` | `java.util.List` |
| `SSL_RETURN_PARAM_TYPE` | `java.security.cert.X509Certificate` |

调用方式（`initZygote` 内）：

```java
XposedHelpers.findAndHookMethod(
    SSL_CLASS_NAME,        // com.android.org.conscrypt.TrustManagerImpl
    null,                  // classLoader
    SSL_METHOD_NAME,       // checkTrustedRecursive
    /* ...参数列表..., */ hook
);
```

算法校验：用同一套 XOR 解出 A 组另一处密文，得到
`"TrustMeAlready loaded! Hooked %d methods"` —— 与开源项目
**TrustMeAlready** 的字符串完全一致，证明解密链路正确。

### 为什么选这一层

`checkTrustedRecursive` 是 Android 系统 TLS 栈（Conscrypt）里真正执行
证书链校验的那一层，返回 `List<X509Certificate>`。

在 `beforeHookedMethod` 里 `setResult(空 List)`，等于告诉调用方
「这条链我认了」，整条校验短路。**不论上层用 OkHttp、
`HttpsURLConnection` 还是 MSDK 自带的原生网络层，都会被覆盖。**

这也解释了 `xposeddescription` 里那句「支持过腾讯健康系统」。

## 三、B 组的现状

B 组没有任何实现 `IXposedHookLoadPackage` 的类，是纯外部 App。
它把 token 交给游戏的唯一手段是 `GameLaunch`：找到游戏的 auth 回调组件，
`startActivity` 把结果塞过去。

作者自己在 `GameLaunch.java` 注释里记录了关键现场：

```
前台: com.tencent.tmgp.dfm/...pixui.webview.WebViewActivity ✓
WindowManager: ...WebViewActivity state from DRAW_PENDING to NO_SURFACE; destroySurface
AppSenseClient: ...WebViewActivity; state: 0; event: GAME ... exit
```

> MSDK 的 WebViewActivity 是「内部页」，靠 Intent 里的 url / title 等参数渲染。
> 我们只给了 auth 数据，它拿不到 url，起来就 destroySurface 退出，
> 留下一个空任务栈 → 黑屏。

## 四、逐项对比

| 能力 | A 组 | B 组 |
|---|---|---|
| 技术形态 | Xposed 注入目标进程 | 独立 App 外部投递 |
| 证书链校验 | 短路 `checkTrustedRecursive` | 无 |
| 健康系统 | 通过（同类手段） | 无 |
| 凭证来源 | 进程内截获 `loginUrl` | WebView 从 URL 抓 `access_token` |
| 三角洲投递 | 不需要投递，进程内直接生效 | `startActivity` → 黑屏 |
| 生效范围 | 全部走系统 TLS 的组件 | 仅少数真在 `startActivityForResult` 等结果的游戏 |

**根本差异**：三角洲的登录在 MSDK 进程内完成校验，
它没有「外部 App 把 auth 塞进来」的入口。
B 组试图投递的那一刻就已经失败了 —— 不是投递得不够好，是这条路不存在。

**顺带纠正一个误判**：B 组里的 Xray / VLESS（`NodeConfig`、`XrayCore`）
是更新下载通道，**不参与登录**，与三角洲登录失败无关。

## 五、重构做法

### 1. 把「投递能力」显式化

新增 `core/GamePlan.java`，每个游戏声明能力位：

| 游戏 | pkg | external | inProcess |
|---|---|---|---|
| 和平 | `com.tencent.tmgp.pubgmhd` | ✓ | |
| 王者 | `com.tencent.tmgp.sgame` | ✓ | |
| 三角洲 | `com.tencent.tmgp.dfm` | | ✓ |
| 暗区突围 | `com.tencent.mf.uam` | ✓ | |
| 无畏契约 | `com.tencent.tmgp.codev` | ✓ | |

调用方先问 `canDispatchExternally(game)`，三角洲会直接得到 `false`，
**不再「先试一次、黑屏、再换下一个」**。

### 2. 补上进程内注入

新增 `core/XposedEntry.java`，沿用 A 组已验证的目标：

- 主路径：`hookAllMethods` 匹配 `TrustManagerImpl#checkTrustedRecursive`，
  按签名特征筛选（返回 `List` + 参数含 `X509Certificate[]` 和 `List`），
  不写死参数个数 —— 该方法在 Android 7 是 5 参、10 以上 6~7 参
- 命中数写进 Xposed 日志，`0` 表示没接上，现场可直接区分「类不在」还是「方法改名」

⚠️ 上一版草稿曾 hook `okhttp3.CertificatePinner` 和
`javax.net.ssl.X509TrustManager`，两者都是错的：
前者只存在于用 OkHttp 做 pinning 的场景，后者是接口，
hook 接口抽象方法不影响任何实现类。已废弃。

### 3. 仍需真机验证的部分

MSDK 登录结果的**回灌**（把截获的 auth 写回 MSDK 的登录回调）
尚未实现，代码里标了 `TODO_MSDK`。

原因：MSDK 的类名与方法名随版本变化，A 组也没有走这条路
（它靠证书绕过让原生登录链路自然走通）。
凭空写死类名只会「编译通过、运行时无效」，所以留待真机日志确认后再补。

## 六、预期效果

| 场景 | 重构前 | 重构后 |
|---|---|---|
| 和平 / 王者 / 暗区 / 无畏 | 可用 | 可用（走 `GameLaunch`） |
| 三角洲 | 黑屏 | **不再黑屏**；证书层已绕过 |
| 三角洲能否完成登录 | — | **取决于是否启用 Xposed 并授予模块作用域** |

**重要**：重构只是把「必然失败」变成「具备前提条件」。
三角洲最终能否登录，还需要：

1. 设备已 root 且安装 LSPosed / EdXposed
2. 本模块在作用域中勾选 `com.tencent.tmgp.dfm`
3. 真机日志确认 `checkTrustedRecursive 已接管 N 个重载` 中 N > 0
